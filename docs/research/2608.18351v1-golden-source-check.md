## 一句话主线

这篇论文研究的是：工具型大模型智能体即使最终完成任务，也可能执行超出任务所需的权限，例如读取无关数据、修改任务范围外的目标或使用更高风险工具。论文提出一种“任务条件下的最小权限”后训练框架，让模型在终端和 MCP 环境中选择足以完成任务、但尽量不超出任务所需权限的动作；框架用 broker 对动作做执行前/执行后审计，用任务特定的足够权限包络线定义“多余权限”，再把任务完成、证据、状态和权限风险纳入可验证奖励。原文报告该策略在其 500 个留出任务、2,896 个评估 episode 上把 safe success 从 64.36% 提升到 98.48%，把成功的 excess-authority 事件从 4.56% 降到 0.79%；作者同时强调这只是权限门禁和沙箱的补充，不能替代强制执行控制。

## 1. 背景与问题发现

### 现实问题

工具型 agent 可以完成 MCP 调用、文件编辑等任务，却仍然可能产生非预期副作用：读取无关记录、修改任务范围外的目标、调用权限更高且风险更大的工具，甚至造成潜在权限升级。作者把“超出一个请求合理所需的最低权限”定义为 task-relative excess-authority error；即便最终答案或状态正确，只要执行轨迹越过任务边界，仍可被视为过度授权轨迹。（Introduction）

### 为什么已有方案不够

论文认为现有 permission gating 主要在模型提出或执行动作之后拦截风险调用，覆盖范围取决于系统能否识别动作类别；功能等价的状态变化可能通过没有同样门控的路径绕过。静态门控还可能同时出现两种问题：没有给执行链实际需要的权限，却授予任务不需要的敏感权限。因此作者希望模型在一开始就更少提出不必要的高权限动作，但仍能提供完成任务所需的证据。（Introduction）

### 问题的准确边界

这不是“让模型拒绝所有危险动作”，也不是普通的工具选择或静态权限分类。任务可能合理需要写入、执行、外部服务访问或持久化状态；关键是根据当前任务判断足够权限，而不是一律偏好低权限动作。论文还把轨迹权限而非单个工具调用作为测量对象，因为命令/调用的意义取决于参数、环境状态和实际效果。（Introduction；Literature Review）

## 2. 核心主张与贡献

### 核心想法

将“最小权限”从静态系统权限约束改成任务相对的、可测量的轨迹属性：先为任务定义足够权限包络线，再测量 agent 轨迹实际达到的权限，只惩罚超过包络线的部分。模型的目标不是不做事，而是以足够的证据和正确状态完成任务，同时少做多余的高风险动作。

### 论文声称的三项主要贡献

1. 使用六维风险向量的 task-relative privilege classification / least-privilege reinforcement-learning framework。
2. 一个带 broker、执行前和执行后审计的终端/MCP 执行环境，以及确定性的 excess-authority 评估数据集。
3. 让权限测量适用于不同任务和环境，而不只适用于训练中见过的任务；但这一点只得到论文所述留出任务和外部测试的有限支持，不应解读为生产环境保证。（Introduction；Limitations）

## 3. 方法：它具体如何解决

### 3.1 轨迹与六维权限表示

对任务 `x`，可见动作包括终端命令、MCP 调用、分类的人类升级请求和最终答案；动作与环境观察组成轨迹 `τ`。每个动作分配六维 authority vector：

`z(a_t) = [write, exec, external, secret, scope, persistent] ∈ [0,1]^6`

六个维度分别表示状态修改、动态执行、是否触及环境边界、非特权敏感数据访问、宽泛/广域影响，以及超出预期操作后仍持续存在的状态。单个动作的风险向量取执行前和执行后评估的逐分量最大值；整条轨迹再对所有动作取逐分量最大值。（Methodology III-A，式(1)(2)）

### 3.2 任务包络线与多余权限

每个任务有经审核的 sufficient-authority envelope `z_req(x)`。轨迹的 excess-authority vector 为：

`Δ(τ,x) = max(z_τ - z_req(x), 0)`

逐维低于任务需求的权限被置零，所以只有超出“完成该任务足够权限包络线”的部分进入多余权限惩罚。这个设计解释了为什么论文不是简单惩罚 write 或 exec：若任务确实需要写入或执行，它们可以在包络线内，不应被视为过权。（Methodology III-A，式(3)）

### 3.3 broker、审计和确定性验证

每条轨迹中，host broker 先分析动作：命令族、flags、路径、重定向、组合方式、工具身份和参数范围等。支持的动作在非 root 容器或可重置 MCP 服务中产生真实效果。执行后再用文件/Git diff、进程遥测、服务记录、敏感路径访问和精确状态变化审计实际影响。最终动作权限取执行前和执行后向量的逐分量最大值，因此被拦截的命令仍能记录“尝试了不合理权限”，而静态解析漏掉的环境影响也能被捕获。（Methodology III-B）

确定性 verifier 检查精确答案、隐藏测试、必需输出文件、目标测试结果、精确 MCP 状态、证据路径、必需写入以及额外写入的拒绝。proposal-only 任务禁止环境修改；升级任务要求有适当且有证据的人工介入理由；最终回答之后的读取不能倒过来为回答提供证据。（Methodology III-B）

### 3.4 safe success 与奖励

论文定义 safe success 为同时满足任务成功、证据足够、任务状态约束满足且没有可报告的 excess-authority 事件：

`SafeSuccess(τ,x) = 1[S=1 ∧ E≥e_x ∧ V_x=1 ∧ O_τ=0]`

它区分“模型尝试了什么”和“环境最终允许什么”：被 broker 阻止的命令可能没有造成外部损害，但仍会记录为不合理权限请求。因此只看 over-privilege 率会奖励“什么都不做”，safe success 则同时要求完成任务。（Methodology III-A；IV-F）

标量奖励为：

`R = 0.60S + 0.20E - 0.20P - 0.05U + 0.10H - 0.75B - 0.05F_u - 0.12F_r`

其中 `P` 综合轨迹多余权限、敏感信息过权、标签置信度和逐步过权；`U` 惩罚动作数量和重复循环；`H` 奖励正确升级；`B` 表示被阻止动作的严重程度；`F_u` 是格式错误或不支持动作；`F_r` 是禁止读取。作者明确说明这些奖励权重是手工选择的，未证明是最优。（Methodology III-D；Limitations）

### 3.5 训练设置

论文用 Qwen3.5-4B，rank-32 LoRA、alpha 64、bfloat16、direct Dr. GRPO，训练一个 1,500-step epoch；每行采样八条轨迹，每条 completion 上限 4,096 token，最多 20 次工具调用，clip 0.2，batch size 1，梯度累积 8，不使用 KL 项和 supervised fine-tuning。主运行环境是 Ubuntu 24.04/WSL、两张 32GB NVIDIA RTX 5090-class GPU，使用 TRL 1.5.1 和 vLLM 0.22.1；三个独立 seed，每个产生 12,000 条训练轨迹。（Methodology III-D）

## 4. 实验如何验证主张

### 数据与划分

作者编写 2,000 个任务：1,500 个训练任务、300 个训练族内验证变体、200 个训练时未出现的 whole-family excluded 任务，合计 500 个留出任务。任务覆盖阅读定位、代码修改和测试、恢复/升级、对抗性约束、MCP/多工具和未见行为族。任务是按结构化 schema/family 合成并用预定义 oracle、权限包络线、确定性 verifier 和负例验证的；这点是外推边界的重要组成部分。（Methodology III-E；Limitations）

完整 500-task 内部评估中，普通任务生成四次，安全敏感任务生成八次，共每个 policy 2,896 episodes。外部评估包括 MetaTool 1,000 项子集、FORTIS 两个任务（600 和 1,543 项）以及 544 个 ToolPrivBench 场景。（Methodology III-E）

### 核心内部结果（Base vs Seed 1）

| 指标 | Base | 训练后 Seed 1 | 变化 |
|---|---:|---:|---:|
| Task episode success | 1,996 (68.92%) | 2,875 (99.27%) | +30.35 pp |
| Safe success | 1,864 (64.36%) | 2,852 (98.48%) | +34.12 pp |
| Excess-authority success | 132 (4.56%) | 23 (0.79%) | -3.77 pp |

作者强调 safe success 的提升伴随普通任务成功率提升，所以不能简单解释为模型通过拒绝执行来降低过权。对完整 200-task whole-family held-out partition，Seed 1 的 safe episodes 是 1,020/1,020，Base 是 689/1,020；未见 MCP family 上为 440/440 对 220/440。（Results IV-A）

### 其他验证与应谨慎解读之处

- 三个 seed 在例行 206-task 评估集上的 safe success 为 85.98%、97.63%、86.29%，作者选择 Seed 1 作为最稳定者后完成完整评估；这不是所有 seed 的完整 500-task 汇总。
- Prompt ablation 中，Seed 1 从完整 prompt 到短 prompt 的 safe success 只从 97.63% 降到 97.39%，但 excess-authority 从 0.73% 增到 1.46%；说明在相似训练接口上行为不完全依赖措辞，但不等于跨环境不依赖 prompt。
- 独立 benchmark：MetaTool accuracy 81.9%→83.6%；FORTIS T2 shared-parse over-privilege 43.28%→40.72%。FORTIS T2 只比较两种 policy 都能解析的 1,250/1,543 项，不能把它当成全部条目的无条件比较。
- 默认 prompt 下 ToolPrivBench over-privilege 45.2%→45.0%，统计上无显著差异；加入 privilege-aware/task-specifying prompt 后为 Base 41.2%、Seed 1 37.9%。这说明外部泛化并不均匀，不能只引用内部 98.48% 得出普遍安全结论。
- 400-task corrective continuation（200 个纠正任务+200 个 rehearsal 任务）使 ToolPrivBench over-privilege 从 45.04% 降到 38.05%，下降 6.99 pp；其 50-task continuation 验证集 safe success 从 67.75% 到 90.50%，同时内部 500-task safe success 仅增加 0.28 pp。该 continuation 从已选 Seed 1 开始，且是事后受外部 benchmark 启发，不能当作无偏的原始泛化实验。（Results IV-D/E）

## 5. 限制、可信范围与不能推出的结论

1. 任务主要由结构化 family 合成，虽有 whole-family holdout 和模板组检查，但不能证明在不受限制的生产仓库或真实服务上同样有效。
2. 六个权限维度、权重和 sufficient envelope 含有人为判断，即使作者为每项任务提供风险归档理由，也不是客观无争议的真值。
3. 只使用一个 4B 模型和一个 adapter family；不能据此推出对更大模型、其他架构或其他 adapter 的通用效果。
4. 训练第 500 步已获得内部 safe-success 能力增益的约 98%，内部任务多样性可能不足；外部 ToolPrivBench 的 prompt-neutral 条件下训练/未训练策略统计上不可区分，部分 failure-escalation family 还出现退化。
5. 训练改变的更像是模型已经会做的行为选择，而不是凭空创造新能力；在没有相似接口结构和任务规格的 OOD 环境，行为可能回到更接近 base policy。
6. 400-task continuation 继承已选 Seed 1，动机是事后产生的，也不是完全无偏的泛化证明；作者明确建议从 base model 开始混合这些任务再实验。
7. 训练稳定性并不保证：两个 seed 在某些未见 MCP family 上出现 malformed arguments；作者提出 SFT cold-start 可能改善稳定性，但本文没有做该验证。
8. reward 权重为手工选择，没有系统测试不同权重组合；因此不能声称当前奖励是最优设计。
9. learned policy 仍须位于普通系统控制之后。它可以减少不必要的高权限请求、改善遵循最小权限规则，但不能提供 permission gate 或 sandbox 的执行保证与确定性故障安全。

## 6. 给读者的最短复述

如果只保留一段：

> 这篇论文不是在做普通的权限分类，而是在解决“agent 完成任务时为什么还会做超出任务需要的事”。作者把任务需要的最低权限表示成一个六维、任务特定的权限包络线，用 broker 对每个终端/MCP 动作做执行前和执行后审计，再用任务成功、证据、精确状态和过权惩罚构成确定性奖励，后训练 Qwen3.5-4B 学会更少提出不必要的高权限动作。论文在自己合成的、带相同 broker/verifier 结构的留出任务上取得很大提升，但外部 benchmark 的收益依赖任务接口和提示词，并不均匀，因此它是权限门禁/沙箱的补充，不是安全保证。

## 7. 黄金验收要求

精读系统至少应让读者先读懂以下因果链，再看实验数字：

`agent 能完成任务但会过权`
→ `静态/事后门控不够，且可能漏门或给错权限`
→ `用任务特定足够权限包络线定义真正需要的权限`
→ `broker 做前后审计，verifier 检查任务/证据/状态，训练奖励同时鼓励完成和克制`
→ `内部合成留出任务有效，但真实生产泛化和执行保证仍未证明`。

若输出只包含 1,500/300/200/500 等任务数字，却没有上述问题发现、方法因果和限制边界，应判为“证据存在但未形成论文理解”。
