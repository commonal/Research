# Task-Conditioned Least-Privilege Learning for Executable Terminal and MCP Agents

## 一句话先说清楚

这篇论文研究的不是“智能体能不能完成任务”，而是：**智能体在完成任务时，能不能只使用完成任务所必需的权限，而不顺手读取无关数据、修改无关文件或调用更高风险的工具。**

作者把这种超出任务需要的行为定义为 task-relative excess-authority error，并提出让模型在训练阶段学会任务条件化的最小权限行为。它不是用一个静态权限表把所有动作一刀切，而是为每个任务定义一个“足够完成任务的权限包络”，再用 broker、前后置审计和确定性校验器判断模型是否越过了这个包络。

核心结论是：在作者设计的终端和 MCP 任务环境中，加入这种权限感知的后训练后，模型在保持任务完成能力的同时，显著减少了超额权限行为；但这只是额外控制层，不能替代权限门禁和沙箱。[原论文摘要与引言](https://arxiv.org/html/2608.18351v1)

## 1. 背景：作者发现了什么问题

工具型 LLM 智能体已经可以调用 MCP 工具、执行终端命令和编辑文件，但“最终任务做对”不代表“执行过程安全”。例如，用户只要求读取 `bug.txt` 并提出补丁，智能体却可能写文件；用户只要求处理一个目标，也可能读取无关记录、访问敏感数据、使用更高权限的工具。

这暴露了传统评测的盲点：如果只看最终答案或最终状态，就会把“完成任务但执行了不必要高权限动作”当成成功。

作者认为现有权限门禁也不充分。静态 gating 可能拦住危险调用，但它可能漏掉功能等价的另一条状态修改路径；也可能一边不给任务真正需要的权限，一边授予任务不需要的敏感权限。因此问题不是简单地“允许/拒绝某个工具”，而是要判断：**对于当前任务、当前参数、当前环境状态和实际后果，这个动作是否超出了足够权限。**

## 2. 论文真正要解决的问题

论文研究的问题可以改写为：

> 能否通过后训练，让一个 4B 级模型在可执行终端和 MCP 环境中，主动选择“足够完成任务但不过度授权”的动作，并把这种能力作为权限门禁和沙箱之外的额外控制层？

这里有两个同时成立的目标：

- 任务仍然要完成，并提供足够的证据和正确状态；
- 模型不能为了方便而执行超出任务需要的写入、执行、外部访问、敏感数据读取、宽范围影响或持久化动作。

## 3. 核心想法：把“最小权限”变成任务相对的可计算目标

论文的关键不是给模型背一张固定权限表，而是为每个任务定义一个 reviewed sufficient-authority envelope（足够权限包络）。

每个动作被映射到六维权限/风险向量：

\[
\mathbf z(a_t)=[z_{write},z_{exec},z_{external},z_{secret},z_{scope},z_{persistent}]
\]

六个维度分别表示状态写入、动态执行、跨环境边界、敏感数据访问、影响范围以及超出当前操作后仍持续存在的状态。

一条轨迹的风险取所有动作在每个维度上的最大值；任务本身也有一个足够权限向量。两者相减并截断为非负，就得到超额权限向量：低于任务需求的权限不受罚，只有超过任务包络的部分才被处罚。

这使论文能够区分两种情况：

- 读 `bug.txt` 并给出建议：写操作是超额权限；
- 从一个 GitHub 类 MCP 服务读取信息并写入另一个数据库：外部访问和写入可能是任务真正需要的权限。

因此“最小权限”不是永远拒绝高风险动作，而是让风险与任务需求绑定。[III-A、III-C](https://arxiv.org/html/2608.18351v1)

## 4. 方法如何落地

执行闭环是：

1. 模型看到完整工具清单并提出终端命令、MCP 调用、人工升级请求或最终答案；
2. 隐藏的 broker 在执行前解析命令族、参数、路径、重定向、组合方式和工具范围，计算预执行风险并决定执行模式；
3. 动作在非 root 容器或可重置的 MCP 服务中执行；
4. 执行后，校验器检查文件/Git diff、进程遥测、服务记录、敏感路径访问和精确状态变化；
5. 确定性 verifier 同时检查任务答案、必需输出、证据路径、应有写入和额外写入；
6. 根据任务成功、证据充分、状态正确、禁止动作、阻断严重性和超额权限计算训练奖励。

论文定义的 safe success 不是“模型答对了”这么简单，而是任务成功、证据达到要求、状态约束满足，并且没有可报告的超额权限事件同时成立。

训练方面，作者使用 Qwen3.5-4B、rank-32 LoRA、bf16 和 direct Dr. GRPO，在 1,500 个任务上训练。奖励函数为：

\[
R=0.60S+0.20E-0.20P-0.05U+0.10H-0.75B-0.05F_u-0.12F_r
\]

其中不仅奖励任务成功和证据，还惩罚轨迹超额权限、重复动作、阻断动作、非法动作和禁止读取。[III-B、III-D](https://arxiv.org/html/2608.18351v1)

## 5. 实验如何验证这个想法

作者构造了 2,000 个任务：

- 1,500 个训练任务；
- 300 个同任务族验证变体；
- 200 个训练中未出现的新任务族。

完整留出验证覆盖 500 个任务，共 2,896 个评测 episode。任务包含定向阅读、代码修改、测试选择、恢复与升级、提示注入克制、秘密诱饵、外部读取、MCP 状态修改和多工具工作流。

在完整 500-task 留出评测中，Seed 1 相对 base policy 的结果是：

| 指标 | Base | Seed 1 |
|---|---:|---:|
| 任务 episode success | 68.92% | 99.27% |
| Safe success | 64.36% | 98.48% |
| 超额权限错误事件 | 4.56% | 0.79% |

这组结果支持的结论是：在该任务环境和校验定义下，训练后的策略既更常完成任务，也更少产生超额权限错误。它不支持“模型已经在真实生产环境中安全”这样的更强结论。

外部评测显示，MetaTool 工具选择准确率从 81.9% 到 83.6%，FORTIS 的共享可解析样本超额权限从 43.28% 降到 40.72%。另外，400-task continuation 在 ToolPrivBench 上把超额权限从 45.04% 降到 38.05%，下降 6.99 个百分点，但这仍然是特定外部基准上的泛化证据，不是生产环境证明。[IV-A—IV-E](https://arxiv.org/html/2608.18351v1)

## 6. 应该怎样解读，而不是过度宣传

这篇论文最有价值的贡献是把“执行任务”和“不要使用多余权限”放进同一个可计算、可训练、可验证的闭环里。它证明了在作者构造的终端/MCP 环境中，权限感知后训练可以成为有效的额外控制层。

但实验不能证明：

- 生产仓库、真实服务和开放式用户请求中同样有效；
- 六个风险维度和每个任务的权限包络一定正确；
- 单个 4B 模型和一个适配器家族的结论能无条件迁移到其他模型；
- 学到的是普遍的安全判断，而不是对任务 schema、提示词和环境约定的适应。

作者也明确说，任务主要由结构化任务族合成，不能据此推出在不受约束的生产仓库或服务中的表现；该方法应与 permission gates 和 sandboxing 叠加使用，而不是替代它们。[V Limitations and Future Work、Abstract](https://arxiv.org/html/2608.18351v1)

## 黄金验收判定

一份生成结果只有在以下四点都做到时，才算真正读懂这篇论文：

1. 先讲清楚“为什么任务完成仍可能是不安全的”；
2. 讲清楚“任务足够权限包络”是核心抽象，而不是泛泛地说动态权限；
3. 讲清楚 broker、六维风险向量、前后置审计和后训练如何连成闭环；
4. 用实验数字验证主张，同时主动说明合成任务、单模型、单环境和不能替代沙箱等边界。

如果只列出 2,000/1,500/300/200 等任务数字，却没有讲清楚上述问题和解决机制，应判定为**证据局部正确但精读失败**。
